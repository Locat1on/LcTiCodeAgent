# LcTiCodeAgent 两分钟视频脚本

## 录制方式

先录制完整的 Web UI 操作，不要现场讲话。任务完成后剪掉等待时间，再按下面的旁白配音。

录屏中不要出现设置 API Key 的终端。建议使用 1920×1080，浏览器缩放保持 100%。模型等待片段可以加速，工具调用、压缩结果、测试结果和审批卡片要保留原速或接近原速。

## 录制前准备

### 1. 确认任务仓库处于失败基线

在项目根目录运行：

```powershell
git -C tmp\video-task-http-cache-20260901 status --short --branch
```

应只显示：

```text
## main
```

如果出现修改文件，不要开始录制，先重新恢复任务基线。

### 2. 启动 Web UI

在不录屏的终端中运行：

```powershell
$env:OPENROUTER_API_KEY = "你的密钥"
$env:LCTI_MAX_STEPS = "64"
$env:LCTI_CONTEXT_BUDGET = "16000"

.\.venv\Scripts\python.exe -m code_agent.web `
  --workspace tmp\video-task-http-cache-20260901 `
  --session-root tmp\video-recording-sessions `
  --live
```

然后打开：

```text
http://127.0.0.1:8765/
```

不要录到设置环境变量的终端，也不要在视频中打开 API Key 输入框。

## 完整操作顺序与输入内容

### Turn 1：只读分析

在 Web 输入框中粘贴：

```text
只读分析 README.md 描述的全部 Mini HTTP Cache production issues。先运行 `python -m unittest tests.test_acceptance -v` 展示代表性行为，再检查实现和所有测试，运行完整 unittest 复现失败，梳理需要修改的模块、状态不变量和实施顺序。当前阶段不要修改任何文件，也不要提交；最后给出基于证据的修复计划。
```

等待 Turn 1 完成。确认画面中出现 acceptance 的 4 个 FAIL、1 个 ERROR，以及最后的修复计划。

### 刷新并恢复 Session

1. 刷新浏览器；
2. 在左侧会话列表选择刚才的会话；
3. 确认历史工具事件重新出现；
4. 打开右侧 Context 面板。

不要点击“新建会话”，否则第二轮无法使用第一轮上下文。

### Turn 2：实施修复

在恢复后的同一会话中粘贴：

```text
现在按上一轮计划实施完整修复。不要修改 mini_cache/models.py、tests 或公共 dataclasses；保持零外部依赖。先重新运行 `python -m unittest tests.test_acceptance -v` 展示行为变化，再运行完整 unittest 直到全绿，检查 Git status 和 diff，并在最终回答中只报告有工具证据支持的结果。
```

发送后应先看到上下文压缩事件，然后进入文件修改和测试。

### Turn 3：仅在 Turn 2 中断时使用

如果 Turn 2 正常给出最终回答，跳过本步骤。如果出现 HTTP 429、连接错误或录屏中断，重新打开同一会话并粘贴：

```text
继续完成刚才中断的收尾。不要再修改实现，除非验证失败；重新确认完整 unittest、Git status 和 diff，然后给出最终任务总结。不要提交。
```

### 展示 Git 一次性审批

任务完成后，在同一会话中粘贴：

```text
请将当前 5 个实现文件提交为一个本地 Git commit，提交信息为 fix HTTP cache semantics。
```

等待审批卡片出现，确认能看到文件、HEAD 和 Secret Scan，然后点击“拒绝”。不要批准，否则任务仓库会产生新提交，不便重新录制。

## 时间轴与旁白

### 0:00-0:12　项目与任务

画面：Web UI 全景，短暂展示顶部模型、Sandbox 和任务仓库。

旁白：

> 这是我从零实现的编程智能体 LcTiCodeAgent。模型生成文本和工具调用，Agent 循环、上下文、工具和安全控制都在本地完成。

### 0:12-0:28　修复前的真实问题

画面：发送上文的 Turn 1 提示词，剪到 `tests.test_acceptance` 的结果，停留在 4 个 FAIL 和 1 个 ERROR。

旁白：

> 这个 HTTP 缓存任务修复前有五个验收场景失败，完整套件有 64 项测试。

### 0:28-0:43　只读分析

画面：快速展示 `list_files`、`read_file`、失败的 `run_command` 和模型提供的 reasoning 文本。最后停在第一轮修复计划。

旁白：

> 第一轮只分析，不修改。Agent 根据 issue、源码和失败测试安排五个模块的修复顺序，过程写入追加式 JSONL 日志。

### 0:43-0:57　会话恢复

画面：刷新页面，从左侧重新打开刚才的会话，展示历史事件和 Context 面板。

旁白：

> 刷新后，系统从日志恢复消息、工作记忆和工具配对，不会重复执行旧工具。旧证据此时可以安全压缩。

### 0:57-1:15　上下文压缩

画面：发送上文的 Turn 2 提示词，重点保留两张压缩事件卡片和 Context 数值变化。

旁白：

> 第二轮先裁剪旧工具结果，再生成结构化摘要。路径、数字、退出码和事件 ID 必须通过本地校验。上下文由四万五千多个估算 token 压到一万三千多个。

### 1:15-1:34　跨模块修改与验证

画面：加速展示五个实现文件的读取、SHA-256、`replace_in_file` 和模块级测试。至少保留一张 State Gate 相关工具卡片。

旁白：

> Agent 按计划修改五个模块。编辑绑定读取时的 SHA-256，文件变化就拒绝旧操作。修改后先跑局部测试，再执行完整回归。

### 1:34-1:48　修复后对比

画面：展示相同 acceptance 命令的 5 个 `ok`，随后展示 `Ran 64 tests` 和 `OK`。

旁白：

> 修复后，同一组测试由五个失败变成五个通过，完整 64 项测试全绿。测试没有改动，Git diff 只包含目标文件。

### 1:48-1:58　安全审批

画面：发送上文的 Git commit 提示词，显示审批卡片、文件列表、Secret Scan 和 Force Disabled，然后点击拒绝。

旁白：

> Git 写操作需要一次性审批。界面先展示变更、HEAD 和凭据扫描；我选择拒绝后，工具不会提交。

### 1:58-2:00　结束

画面：回到 Web UI 全景或项目名称。

旁白：

> 这就是完整的任务闭环。

## 剪辑清单

必须保留：

1. 修复前 acceptance 的 4 FAIL + 1 ERROR；
2. 第一轮只读分析的工具轨迹；
3. 刷新后从会话列表恢复；
4. 确定性裁剪和结构化摘要成功事件；
5. 至少一次 `read_file → replace_in_file`；
6. 修复后 acceptance 的 5 个 `ok`；
7. `Ran 64 tests ... OK`；
8. Git diff 或修改文件列表；
9. Git commit 审批卡片和拒绝结果。

可以剪掉：

- 模型等待时的静止画面；
- 重复读取测试文件；
- 多次相同的压缩检查；
- 完整长测试栈，只保留代表性失败和最后全绿；
- Provider 返回的大段 reasoning 文本，只留能看清标题和用途的一小段。

## 429 或其他异常的处理

正式录制没有发生错误时，直接使用两轮流程。

如果再次遇到 HTTP 429，可以保留 1-2 秒错误画面，然后重新打开同一 Session，发送“完整操作顺序”中的 Turn 3 提示词。

旁白补充一句：

> Provider 限流被明确记录，恢复会话后可以继续验证，不会把错误误报成任务完成。

不要为了让视频看起来顺利而把测试失败、工具拒绝或 Provider 错误伪装成成功。
