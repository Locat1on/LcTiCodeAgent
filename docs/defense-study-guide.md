本文用于准备项目介绍和评委问答。目标不是背诵功能列表，而是理解每个设计选择解决了什么问题、为什么没有采用其他方案、证据是什么，以及边界在哪里。

## 1. 推荐学习方法

### 第一遍：先掌握一条主线

先记住一句话：

> LcTiCodeAgent 自行实现 Agent Loop，通过本地工具完成编程任务，并用可恢复上下文和模型外部安全管线保证长任务中的证据连续性与操作可控性。

所有模块都应能归入这条主线：

```text
模型负责提出下一步动作
→ Harness 解析动作
→ 安全管线决定动作能否执行
→ 本地工具产生真实证据
→ 上下文管理保留关键状态
→ 模型依据证据继续
→ 事件日志支持审计和恢复
```

### 第二遍：按“问题—选择—证据—边界”理解

例如，不要只背“项目使用 JSONL”，而要能回答：

- 问题：长任务可能中断，内存历史会丢失；
- 选择：每个 AgentEvent 追加写入 JSONL；
- 证据：Session restore 能重建消息、WorkingMemory 和 tool-call 配对；
- 边界：JSONL 查询效率不如数据库，适合单机项目而非大规模多租户系统。

### 第三遍：脱稿回答

每个问题先用 20–40 秒回答。如果评委继续追问，再补充代码位置、实验数据和局限。不要一开始就把所有细节全部讲完。

## 2. 90 秒项目介绍稿

下面这段可以直接练习口述，但建议理解后用自己的语言表达。

> 我的项目叫 LcTiCodeAgent，是一个从零实现的本地编程智能体。它没有使用 LangChain 或 OpenAI Agents SDK，也没有调用服务端托管的代码执行工具。模型只负责生成文本和 Tool Call，工具定义、流式参数重组、Agent 循环、本地执行、上下文管理、审批和错误处理都由项目自己完成。
>
> 整个运行过程是一个闭环：模型先检查仓库，调用搜索、读文件、编辑和测试工具；每个工具结果再回传给模型，模型根据真实证据继续，直到测试通过或达到明确终止条件。CLI 和 Web UI 共用同一个 Agent、事件协议和 JSONL Session 日志。
>
> 我重点做了两个设计。第一是可验证、可恢复的上下文管理。系统先对旧工具结果做确定性裁剪，再使用固定 Schema 的结构化摘要；摘要中的路径、标识符、数字、退出码和事件 ID 必须能在原始事件中找到，完整证据还可以通过 event ID 回溯。第二是模型外部安全管线。所有 Tool Call 都经过 ALLOW、ASK、DENY 权限判断，文件编辑绑定读取时 SHA-256，网络和 Git 写操作需要一次性审批，批准后还会重新检查状态。
>
> 在视频任务中，Agent 用 5 分 42 秒完成了一个跨 5 个模块的 HTTP 缓存修复。过程包含 Session 恢复、两级上下文压缩、64 项测试和一次 Provider 限流后的继续执行。这个任务主要展示的不是模型本身会写代码，而是 Harness 如何让模型在长任务中安全、可恢复、基于证据地完成工作。

## 3. 一页架构速记

### 3.1 六层结构

| 层次 | 关键问题 | 实现 |
|---|---|---|
| 交互层 | 用户如何观察和控制 Agent | CLI、Starlette Web UI、WebSocket |
| Agent Loop | 何时请求模型、执行工具、继续或停止 | `live_agent.py` |
| Provider 层 | 如何处理流式文本、reasoning 和 Tool Call | `openrouter.py`、`model.py` |
| 工具层 | 模型能做哪些本地动作 | `tools.py`、`command.py`、`network.py`、`git_tools.py` |
| 上下文层 | 如何控制历史增长并保留任务状态 | `context.py`、`summary.py`、`restore.py` |
| 事件层 | 如何审计、恢复和驱动 UI | `events.py`、`session.py` |

### 3.2 一次模型步骤

```text
ContextManager.messages()
  → Provider.stream(messages, tool schemas)
  → TEXT / REASONING / TOOL_CALL / USAGE
  → ToolCallAccumulator 完成 JSON 重组
  → PermissionPolicy
  → ToolRegistry.execute()
  → Tool Result 写入 Context + SessionLog
  → 下一模型步骤
```

### 3.3 三条核心不变量

1. **工具结果必须由本地执行器产生**：模型不能自己声明工具执行成功。
2. **Assistant Tool Call 必须与 Tool Result 配对**：压缩和恢复不能破坏协议结构。
3. **高风险授权与具体状态绑定**：一次批准不能复用到后来发生变化的文件或 Git HEAD。

## 4. 五个必须讲清楚的设计决策

### 4.1 为什么自行实现 Agent Harness

**问题**：如果直接使用 Agent SDK，核心循环、工具调度和错误处理会被框架隐藏，无法证明自己理解 Agent 如何运行。

**选择**：仅使用普通 OpenAI-compatible 客户端，自己实现：

- 流式输出解析；
- Tool Call 参数分片重组；
- JSON 参数检查；
- 多步循环；
- 工具执行与结果回传；
- 终止条件；
- Session 持久化与恢复。

**证据**：`ToolCallAccumulator`、`LiveAgent.respond()`、`ToolRegistry` 和 `project_session()` 都是项目代码。

**边界**：项目仍使用 `openai` Python 包发 HTTP 请求，但它只是模型客户端，不提供 Agent Loop 或本地工具执行。

### 4.2 为什么使用追加式事件日志

**问题**：聊天消息列表不足以表示审批、工具开始/失败、上下文压缩和中断状态；只保存在内存中也无法恢复。

**选择**：把用户、模型、工具、审批、usage、压缩和终止统一为 `AgentEvent`，逐行追加到 JSONL。

**优点**：

- 进程异常时，已写入事件不会被整体破坏；
- CLI、Web UI、恢复和评测共用同一事实来源；
- 可以从 event ID 回溯完整工具证据；
- 能判断工具调用是否在中途被打断。

**边界**：JSONL 适合单机顺序日志，不适合高并发查询。如果扩展为多用户服务，应迁移到数据库或事件存储。

### 4.3 为什么上下文采用“两级压缩 + 回溯”

**问题**：不压缩会不断增加 token；删除最旧消息可能丢失任务目标和测试证据；普通摘要又可能虚构路径或退出码。

**选择**：

1. 60% 时优先执行确定性工具结果裁剪；
2. 75% 时尝试固定 Schema 的结构化摘要；
3. 以 50% 为软目标；
4. 原始 JSONL 永不因压缩改写，event ID 可恢复完整证据。

**为什么先确定性裁剪**：测试日志和文件正文结构明确，可以用纯函数保留退出码、错误尾部、路径和事件指针，不必承担模型摘要风险。

**为什么还需要 LLM 摘要**：确定性规则只能压缩工具结果，不能很好地抽取跨多轮的目标、决策和下一步。

**边界**：事实校验只能证明受保护字段来自源事件，不能证明自由文本完全语义等价；真实对比中 validated 的总 prompt token 也没有稳定优于基线。

### 4.4 为什么安全必须在模型外部

**问题**：系统提示词只能影响模型行为，不能作为权限边界。模型可能误解用户、受到仓库提示注入，或生成危险工具参数。

**选择**：每个 Tool Call 必须经过：

```text
Capability Gate
→ ALLOW / ASK / DENY
→ 参数与路径检查
→ 可选一次性审批
→ 批准后状态复核
→ 执行与审计
```

**关键机制**：

- 未注册工具默认 DENY；
- 文件路径必须解析到工作区内；
- 凭据文件拒绝访问；
- `replace_in_file` 绑定读取时 SHA-256；
- 命令使用数组参数和 `shell=False`；
- Git commit/push 绑定 Preflight 状态令牌；
- push 不提供 force、delete、mirror 或任意 refspec。

**边界**：这是应用层 Workspace Policy，不是 OS Sandbox。被允许运行的测试代码仍以当前 Windows 用户权限执行。

### 4.5 为什么 CLI 和 Web UI 共用事件协议

**问题**：如果 Web UI 重新实现一套 Agent，容易出现安全和状态语义不一致，也会变成界面套壳。

**选择**：`LiveAgent` 只产生 `AgentEvent`，CLI 和 WebSocket 分别消费同一事件流。审批结果也通过统一的 `ApprovalHandler` 返回 Agent。

**优点**：

- 两个界面看到相同工具、错误和上下文状态；
- Web UI 不持有 API Key，也不能直接执行工具；
- 同一个 JSONL 可以被 CLI 或 Web 恢复；
- UI 改动不会改变 Agent 的核心能力。

**边界**：Web 停止是协作式取消，只能在下一个 Agent 事件边界生效，不能强杀正在等待的模型 HTTP 请求。

## 5. 上下文管理必须真正理解的细节

### 5.1 到底是三层还是四层

模型消息有三层：

- `Pinned`：系统提示词；
- `Recent`：当前和最近 turn；
- `Evidence`：较旧、可以裁剪的工具证据。

`WorkingMemory` 独立维护修改文件、验证命令和未解决错误。Web UI 把三层消息与 WorkingMemory 合并呈现为四类信息，所以不能简单说代码里有四个 `ContextLayer`。

### 5.2 为什么当前 turn 不压缩

当前 turn 可能存在已经声明但尚未获得结果的 Tool Call。如果直接删除或摘要，下一次模型请求会出现 assistant/tool 不配对。

因此预算是软触发线。当前 turn 可以暂时超过预算；等 turn 完成后，它转入 Evidence，下一 turn 才安全压缩。视频彩排中，Turn 1 超过 16k 但 `changed=false`，Turn 2 恢复后才真正裁剪 18 条旧工具结果。

### 5.3 摘要如何做事实校验

固定 Schema 包含：目标、完成事项、决策、文件、标识符、命令、退出码、未解决错误、下一步和 event ID。

本地校验器执行：

- 字段必须完整且不能增加额外字段；
- 类型和数组长度必须满足限制；
- 文件、标识符、数字和退出码必须在源消息中出现；
- event ID 必须属于被摘要的源工具事件。

如果验证失败，摘要不会应用，原上下文继续保留。彩排中出现过多次 rejected，随后一次合法摘要才被接受。这说明安全边界不依赖模型一定生成正确 JSON。

### 5.4 为什么要保留 recall

摘要适合继续推理，不适合作为最终审计证据。`recall(event_id)` 从不可变 JSONL 取回原始工具事件，使用户能够核对测试日志、命令输出和错误详情。

### 5.5 阈值为什么是 60%、75%、50%

这三个数是工程策略，不是数学最优解：

- 60%：给确定性裁剪留出提前量；
- 75%：只有裁剪不足时才付出 LLM 摘要成本；
- 50%：为后续工具结果留出约一半空间。

答辩时应主动说明它们可通过更多任务实验继续调优。目前价值在于机制可解释、可比较，而不是证明这组数全局最优。

## 6. 安全机制必须真正理解的细节

### 6.1 SHA-256 State Gate 解决什么问题

模型读取文件后，文件可能被用户、IDE 或另一个进程修改。如果模型仍基于旧文本编辑，会发生 TOCTOU 状态竞争。

`read_file` 返回整个文件哈希；`replace_in_file` 必须携带 `expected_sha256`。执行时重新计算哈希，不一致就拒绝。模型只能重新读取后再次编辑。

它不是用来防碰撞攻击，而是把“批准/决策时看到的状态”和“执行时的状态”绑定起来。

### 6.2 为什么编辑采用精确替换

精确替换要求 `old_text` 在文件中只出现一次，可以避免模糊定位和整文件覆盖。配合 SHA-256 后，编辑对象和文件版本都明确。

代价是大型重构效率不高，模型也可能因空格或文本不精确导致第一次替换失败。视频任务中，Agent 会根据失败结果重新读取或修正，而不是绕过 State Gate。

### 6.3 为什么网络是 ASK

网络请求会把 URL 和请求行为带出本机边界。`fetch_url` 因此每次请求都需要批准，并限制为 HTTPS GET/HEAD、公开地址和文本响应。

当前实现会检查初始和重定向后的地址，但没有把实际连接固定到已验证 IP，因此不能宣称完全抵御 DNS rebinding。

### 6.4 Git commit 和 push 为什么都要审批

commit 会改变本地历史，push 会改变外部仓库，两者风险等级不同但都不可仅凭模型意图执行。

Preflight 展示文件、HEAD、Diff 和 Secret Scan；批准后重新计算状态令牌。push 只允许当前 HEAD 到同名分支，不允许 force。这体现最小权限和状态绑定授权。

### 6.5 为什么不用 Docker 做默认 Sandbox

本项目的目标是低门槛本地编程 Agent。Docker 会增加安装、镜像和平台成本，所以默认使用 Workspace Policy。

这是一项明确取舍：它能防模型通过工具接口直接越界，但不能隔离被允许执行的恶意测试代码。如果处理不可信仓库，应额外使用容器、虚拟机或成熟 OS Sandbox。

## 7. Provider、错误处理和恢复

### 7.1 为什么 Tool Call 要等流结束再执行

工具名和 JSON 参数可能被拆成多个增量。如果收到一部分参数就执行，可能使用不完整数据，也会使网络重试造成重复副作用。

项目先在 `ToolCallAccumulator` 中重组并校验，流结束后才交给工具层。

### 7.2 为什么部分输出后不自动重试

如果模型已经输出文字或 Tool Call，再自动重放请求可能导致重复文本或重复工具操作。因此只有在尚未向上层发出任何输出时才自动重试。

视频彩排中的 HTTP 429 发生在已有完整过程之后，系统选择显式报错而不是隐藏重放。用户随后恢复 Session 完成收尾。

### 7.3 中断的工具调用如何恢复

如果日志中存在 assistant 声明的 Tool Call，但没有完成或失败事件，恢复器会合成一条 `ok=false` 的 Tool Result，明确说明工具未执行。

这既保持消息协议合法，也防止模型把“请求过工具”误认为“工具已经执行”。

### 7.4 多厂商支持是怎么实现的

项目使用统一 OpenAI-compatible Chat Completions 传输层，根据 provider ID 选择 Base URL、模型和厂商专属参数。

- OpenRouter 保留 provider routing、`data_collection=deny` 和 reasoning 配置；
- Google、DeepSeek、OpenAI 不接收 OpenRouter 专属字段；
- 自定义接口必须使用 HTTPS；
- API Key 可来自环境变量，或经 Web 输入后仅保存于后端进程内存；
- 切换 Provider 创建新 Session，恢复旧 Session 使用原 provider/model。

边界是：真实端到端证据主要来自 OpenRouter，其他直连厂商目前只有配置和协议测试。

### 7.5 为什么不展示完整思维链

系统只能展示 Provider 明确返回的 `reasoning.summary` 或 `reasoning.text`。加密块和签名不发送浏览器，也不能把提供商文本等同于模型完整内部思维链。

设计重点是让用户看到可验证的外部过程：搜索了什么、调用了什么工具、测试退出码是什么，而不是依赖不可验证的内部思考。

## 9. 高频问答：总体设计

### Q1：你的 Agent 和直接调用大模型有什么区别？

直接调用模型通常只得到一次文本回答。我的 Agent 把模型放进多步反馈循环：模型提出 Tool Call，本地执行器产生真实结果，再把结果返回模型继续决策。文件修改、测试和 Git 状态都来自工具证据，而不是模型自述。

### Q2：项目最核心的创新是什么？

我认为有两个：可验证、可恢复的上下文管理，以及模型外部的安全执行管线。前者解决长任务中的信息增长和证据丢失，后者解决模型提示词不能作为真实权限边界的问题。

### Q3：为什么做 Web UI，不只做 CLI？

Web UI 更适合展示长任务中的工具轨迹、上下文、审批和 Git Preflight。但它不是另一套 Agent，只消费同一 `AgentEvent`，所以增加可观察性而不复制核心逻辑。

### Q4：这是不是给 OpenRouter 套了一个界面？

不是。OpenRouter 只提供模型响应。Tool Call 重组、循环、工具执行、权限、上下文压缩、日志和恢复都在本地实现；即使换成其他兼容模型，这些逻辑仍然存在。

### Q5：为什么不使用现成 Agent 框架？

一是项目要求理解和实现核心逻辑；二是自行实现能明确控制工具边界、重试幂等性和压缩不变量。代价是功能覆盖和生态不如成熟框架，但设计更透明、可答辩。

### Q6：模型和 Harness 谁贡献更大？

两者共同决定结果。模型负责理解问题和生成动作，Harness 决定它能看到什么证据、能执行哪些动作、失败后是否安全继续。固定模型比较不同 Harness 才能更接近测 Harness；固定 Harness 比较模型才更接近测模型。

## 10. 高频问答：Agent Loop 与工具

### Q7：Agent 怎么知道何时停止？

模型没有 Tool Call 并返回正常 finish reason 时结束；此外还有步骤上限、模型错误、解析错误、Web 错误和用户取消。默认最大 16 步，避免模型无限循环；长任务可以显式提高到 64。

### Q8：为什么视频任务需要 64 步，默认 16 步是不是不合理？

16 是日常小任务的保守默认值，用于控制失控循环和成本。视频任务有 5 个模块和 64 项测试，因此显式提高预算。彩排证明复杂任务需要更高预算，未来可以根据任务类型或剩余上下文动态调整，而不是把所有任务默认设为 64。

### Q9：如果模型调用不存在的工具怎么办？

Tool Call 先通过解析器，再由 `ToolRegistry` 精确查名；`PermissionPolicy` 对未知能力默认 DENY。大小写变体、尾随空格或伪造批准参数不会命中合法能力。

### Q10：工具失败后 Agent 怎么处理？

失败也会生成 Tool Result 返回模型。系统提示词要求读取错误并改变方案，不能原样盲重试。安全策略拒绝、用户拒绝和真实执行错误都会被区分并写入日志。

### Q11：模型能不能伪造测试通过？

模型可以输出虚假文字，但系统不会把文字当执行结果。`run_command` 的 argv、stdout、stderr 和 exit code 由本地子进程生成；最终成功声明要求有 exit code 0 的验证证据。

### Q12：为什么不用通用 Shell 工具？

通用 Shell 表达能力强，但也使重定向、命令拼接和网络行为难以约束。项目只接受参数数组并使用 allowlist，牺牲部分灵活性换取可审计边界。

### Q13：为什么没有任意文件删除和移动？

当前项目优先覆盖读取、搜索、精确修改、新建和验证这些核心动作。删除和移动更难恢复，容易扩大破坏面。它们可以作为后续受审批能力加入，但不是本版本的默认工具。

## 11. 高频问答：上下文管理

### Q14：为什么不直接删最旧消息？

最旧消息可能包含用户目标、修改原因和唯一测试证据，删除后模型会重复读取或做出错误判断。项目提供 drop-oldest 作为对比基线，但默认使用保留证据指针的裁剪和结构化摘要。

### Q15：为什么普通摘要不够？

普通摘要可读，但可能生成源事件中不存在的文件名、数字或退出码。我的方法要求固定 Schema，并在本地验证受保护事实；验证失败时不应用摘要。

### Q16：事实校验是不是能保证摘要完全正确？

不能。它能保证路径、标识符、数字、退出码和 event ID 有来源，但自由文本可能仍然遗漏关系或改变语义。因此我保留原始日志和 recall，并把这一点列为已知限制。

### Q17：为什么摘要被拒绝后还继续运行？

摘要只是优化，不应成为任务可用性的单点故障。拒绝后保留原上下文，Agent 可以继续；代价是 token 和延迟增加。视频彩排中就出现过 rejected 后继续，证明回退路径有效。

### Q18：为什么压缩后还能恢复原证据？

压缩只修改 Context 投影，不修改追加式 JSONL。裁剪项保留 `source_event_id`，`recall()` 直接从日志取回完整事件。

### Q19：WorkingMemory 和摘要有什么区别？

WorkingMemory 是由工具结果确定性提取的结构化状态，如修改文件哈希、验证命令和未解决错误；摘要由模型归纳跨轮目标和决策。前者更可靠但表达能力有限，后者表达力强但需要事实校验。

### Q20：为什么视频要用 16k，不用默认 32k？

目的是在 5–6 分钟任务内可靠展示同一机制。阈值比例和算法没有变化，只缩小演示窗口。正式默认 32k 更适合日常使用，16k 是可复现的演示配置。

### Q21：你能证明上下文方法比基线好吗？

能证明它在一次真实任务中取得最强单次压缩比例 0.2315，并保留可恢复事件；不能证明总 prompt token 总是更低。那次 validated 因摘要校验拒绝和额外读取，总 prompt token 没有优于所有基线。我的结论是它提高了可验证性和可恢复性，而不是宣称绝对省 token。

## 12. 高频问答：安全

### Q22：提示注入时模型会不会读取 `.env`？

模型可能尝试，但文件工具会在模型外拒绝凭据路径。红队测试使用中毒 README、隐藏 Unicode 和伪造成功输出，验证危险调用不能绕过 Capability Gate。

### Q23：测试代码本身恶意怎么办？

这是 Workspace Policy 的边界。`run_command` 可以限制模型发起什么命令，也会移除 API Key 环境变量，但被批准运行的测试仍拥有当前用户权限。对真正不可信仓库必须再加容器、虚拟机或 OS Sandbox。

### Q24：批准网络后，模型是不是可以无限联网？

不可以。批准绑定单次 `ApprovalRequest`，没有永久批准缓存。下一次 `fetch_url` 仍要重新申请，而且 URL 还要经过 HTTPS、公开地址和响应类型检查。

### Q25：为什么 Git 批准后还要检查一次？

审批到执行之间文件或 HEAD 可能变化。Preflight 生成状态令牌，批准后重算；不同就拒绝。这与文件编辑的 SHA-256 State Gate 是同一种 TOCTOU 防护思想。

### Q26：Secret Scan 能保证绝不泄漏密钥吗？

不能保证。它只识别高置信度模式，是最后一道防线；主要措施是密钥只从环境变量或后端进程内存进入 Provider，不传给工具子进程，也不写入日志和浏览器持久化存储。未知格式或经过编码的秘密可能无法识别。

### Q27：为什么称为 Sandbox 会不会夸大？

文档中明确称为 Workspace Policy Sandbox，并主动说明不是 OS-enforced Sandbox。它隔离的是 Agent 工具能力，不是整个 Windows 进程。准确命名和边界声明比追求“绝对安全”更重要。

## 13. 高频问答：Session、Web 与可靠性

### Q28：恢复 Session 会不会重新执行旧工具？

不会。恢复只投影 JSONL，不调用模型、不执行工具、不重新读取文件。中断且没有结果的 Tool Call 会被标记为未执行，模型若仍需要必须重新请求。

### Q29：为什么会话重命名也用事件？

重命名追加 `session.renamed`，不修改旧日志，使会话历史仍然是 append-only。列表读取最后一条重命名事件作为标题。

### Q30：删除会话为什么移到 `.trash`？

直接删除 JSONL 不易恢复。软删除从默认列表移除，但保留人工恢复可能；活动 WebSocket 会话拒绝删除，防止后台线程又创建同名日志。

### Q31：Web UI 如何保证 API Key 不泄漏？

密钥可以来自后端环境变量，也可以通过密码输入框提交到 localhost 并只保存在后端进程内存。接口不回显密钥，前端不写 Local Storage、Cookie 或 Session 日志。Web 输入更方便，但密钥会短暂经过浏览器内存和本机 HTTP 请求；环境变量方式仍更适合录屏和自动化。

### Q32：为什么使用 Starlette，不使用 FastAPI？

项目只需要静态文件、少量 HTTP API 和 WebSocket。Starlette 提供更薄的 ASGI 层，避免引入不需要的自动数据模型和接口层；前端也使用原生 HTML/CSS/JS，降低构建复杂度。

### Q33：HTTP 429 为什么没有被自动重试成功？

默认最多重试两次，但只有在尚未输出任何内容时才能安全重试。该 429 出现在已有工具和文本状态之后，自动重放有重复副作用风险，所以系统显式失败，随后由 Session restore 继续。

### Q34：Web 停止为什么不是立即停止？

同步 Provider 或工具调用不能被安全强杀。Web 设置取消标记，并在下一个 AgentEvent 边界关闭生成器；等待审批时会同时 fail-closed。这个设计保证状态一致，但牺牲了毫秒级中断。

## 14. 高频问答：评测与视频

### Q35：视频任务是在测模型还是测 Agent？

测的是端到端系统。固定 Gemini 后，结果仍由系统提示词、工具、循环、上下文和安全策略共同决定。任务的目的不是给模型排名，而是展示 Harness 如何支撑长任务。

### Q36：为什么不直接用官方 SWE-bench？

官方判分需要特定 commit、环境和测试补丁，通常还依赖 Docker/Linux；在 Windows 上只运行某个仓库不能称为官方成绩。公开视频任务更需要稳定、无污染和可解释，所以采用相同的仓库 issue 形式，但使用自建、固定、可审计测试。

### Q37：自建任务会不会故意迎合自己的 Agent？

有这个风险，所以任务在运行前冻结要求和测试，并先用隔离 gold 验证可解。任务涉及 5 个模块和 64 项测试，修复前后运行同一 acceptance tests；不能根据模型失败临时改变评分标准。

### Q38：为什么视频中需要三轮，不是一次完成？

正常设计是两轮：先分析、后实施，这使旧证据可以安全进入压缩。彩排的第三轮来自真实 Provider 429，只负责恢复和收尾。如果正式录制没有错误，两轮即可完成；出现错误时第三轮正好展示恢复能力。

### Q39：视频剪辑会不会掩盖失败？

可以剪等待和重复输出，但不应伪造顺序或删除关键失败。建议保留初始 acceptance 失败、压缩事件、最终同组测试全绿和 Git diff，让观众能看见真实状态变化。

## 15. 压力追问与答题边界

### 追问 1：你的摘要校验只是字符串匹配，创新性是不是很弱？

可以回答：确实不是完整语义验证，我没有这样宣称。它的价值是把最容易产生错误且最影响编程任务的路径、标识符、数字、退出码和事件 ID 变成可执行约束，再用原始事件回溯覆盖剩余不确定性。未来可以增加语义一致性或双模型核验，但会增加成本。

### 追问 2：上下文超过 100%，说明管理失败了吗？

可以回答：这是软预算和消息配对不变量的结果。系统不会破坏当前活跃 turn；完整旧 turn 才能压缩。视频中的下一轮实际完成了 50,700→33,965 和 45,558→13,597，说明机制在安全时机生效。当前实现仍可进一步增加单 turn 输出限制，这是改进点。

### 追问 3：你的 validated 策略 token 反而更多，为什么还保留？

可以回答：它优化的不只是 token，还优化事实约束和可恢复性。一次实验不能证明成本优势，所以我没有做绝对声明；保留四种策略就是为了让这个问题可测，而不是只展示有利结果。

### 追问 4：既然 Sandbox 不能防恶意测试，安全功能是不是没有意义？

可以回答：威胁模型不同。它有效降低模型误操作、越界文件访问、任意 Shell、无审批联网和 force push 风险，但不替代系统隔离。安全工程应明确能防什么和不能防什么，而不是只有“绝对安全”才有价值。

### 追问 5：模型如果坚持重复失败调用怎么办？

可以回答：提示词要求改变方案，工具失败会返回明确证据，循环还有最大步骤数。当前没有复杂的重复动作检测器，这是可以进一步增加的 Harness 级策略。

### 追问 6：为什么不用向量数据库做长期记忆？

可以回答：本项目重点是单仓库编程任务的短中期上下文，关键状态规模不大。WorkingMemory 加结构化摘要更透明、可测试；向量检索会引入 embedding、召回误差和额外依赖。若扩展到跨项目长期知识，再考虑向量检索更合理。

### 追问 7：为什么使用 SHA-256，不直接依赖 Git？

可以回答：并非所有文件都已被 Git 跟踪，而且 Git 状态不能精确表示模型读取时的文件版本。SHA-256 对每次读取都适用，Git 状态令牌则用于 commit/push，两者覆盖不同层次。

### 追问 8：为什么直接模型厂商没有完整真实测试？

可以回答：实现通过协议和配置测试，但我只有 OpenRouter 的主要真实运行证据，所以不会把直连兼容性包装成完全验证。若继续开发，应为每家厂商加入最小真实 Tool Call 冒烟和能力矩阵。

## 16. 容易答错的句子

不要说：

- “我的 Sandbox 可以安全运行任意恶意代码。”
- “结构化摘要保证内容百分之百正确。”
- “上下文压缩一定比不压缩省 token。”
- “UI 展示的是模型完整思维链。”
- “所有厂商 API 都已经真实验证。”
- “视频任务是官方 SWE-bench 成绩。”
- “测试通过是因为模型说通过了。”
- “上下文绝不会超过设置预算。”

建议说：

- “Sandbox 限制 Agent 工具能力，不替代 OS 隔离。”
- “本地校验约束关键事实来源，剩余风险由 recall 和原日志覆盖。”
- “当前证据支持可恢复性和单次压缩效果，不支持绝对 token 优势。”
- “UI 展示 Provider 返回的摘要或推理文本，不等同于完整内部思维链。”
- “OpenRouter 有真实端到端证据，其他厂商完成了协议级验证。”
- “视频任务采用仓库 issue 形式，用于展示端到端 Harness。”
- “测试结论来自本地命令的 exit code 0。”
- “预算是压缩触发线，当前 turn 为保持协议合法可能暂时超出。”

## 18. 最后十分钟速记卡

### 一句话

从零实现的本地编程 Agent，用可恢复上下文和模型外部安全管线支撑长任务。

### 两个核心点

1. 确定性裁剪 + 事实校验摘要 + event recall；
2. Capability Gate + State Gate + 一次性审批 + Evidence Ledger。

### 三个数字

- 60% 裁剪；
- 75% 摘要；
- 50% 软目标。

### 三条边界

- Sandbox 不是 OS 隔离；
- 摘要校验不是完整语义证明；
- 压缩不保证总 token 一定更少。

### 四项证据

- 项目自身 191 项测试；
- 视频任务 64 项测试；
- 完整彩排 5 分 42 秒；
- 两次确定性裁剪和两次通过校验的结构化摘要。

### 回答公式

```text
结论
→ 解决的问题
→ 实现机制
→ 代码或实验证据
→ 主动说明边界
```
